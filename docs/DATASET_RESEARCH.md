# Echo dataset research and local VL model plan

[README](../README.md#dataset-research-an-open-source-vision-language-model-for-local-use) · [Vibe coding](VIBE_CODING.md) · [Recording implementation notes](dataset-recording-2026-10-02.md)

Deepak is building a dataset through Echo with the goal of training an open-source vision-language model for local inference. The intended capability is to interpret a goal and the observed desktop, choose a valid next tool action, and improve through verified feedback.

The planned path is **saved Echo trajectories → synthetic examples → manual editing and gold-standard review → SFT → GRPO → held-out evaluation and local deployment**. This is a research plan; no training or benchmark result is claimed by the inventory below.

## What Echo records now

The [trajectory recorder](../src/learn/trajectory.ts) stores task/turn identifiers, the recorded source and declared model, the user's command, the observation available to the model, tool arguments, action permission and a result. Outcome labels are separate records and can be superseded by a later label for the same turn.

An observation can be a screenshot, OCR text or an Accessibility-tree representation. A screenshot is paired with the action using the observation already seen by the model, rather than taking a new image after the action. This preserves the before-action state needed for visual grounding.

The [dataset exporter](../src/learn/dataset-export.ts) can save available run recordings, conversations, trajectories, screenshots, coding evidence and tool schemas. It preserves provenance and labels training candidates. Its `gold.jsonl` starts empty; raw records and automatic success labels are not automatically certified gold.

## Planned synthetic data and manual gold review

Deepak plans to derive synthetic datasets from Echo's saved records, then manually edit and verify them. Possible variants include rephrased goals, corrected action targets, alternative valid tool calls, failure/recovery examples and multi-step task decompositions grounded in the recorded state.

Synthetic examples should retain their parent trajectory and generation provenance. Rephrasing a task does not create evidence that an unavailable control existed or that an unobserved action succeeded. Corrections need to match the screenshot, available tools and observed outcome. Failure/refusal records can inform appropriate rejection or recovery examples rather than being copied as successful action targets.

Gold-standard promotion is planned to require manual inspection of image–task–action alignment, exact tool schemas, outcome evidence and sensitive content. The reviewer can correct, reject or approve an example and record why. The current exporter does not carry out this manual certification.

Real tasks, near-duplicates and their synthetic descendants should stay in the same split group. Held-out tasks must remain separate from SFT examples and GRPO optimization so evaluation measures more than memorization of familiar screens or templates.

## Planned SFT and GRPO stages

1. **SFT — supervised fine-tuning.** Train the selected open-source VL base on reviewed image/text observations and target actions. Text-only examples can support tool syntax and selection, while image-paired examples support visual grounding. The trainer and image processing must match the chosen base. [TRL's SFT documentation](https://huggingface.co/docs/trl/main/en/sft_trainer) describes supervised training and its vision-language dataset support.
2. **GRPO — Group Relative Policy Optimization.** After an SFT baseline, sample groups of candidate outputs or controlled rollouts and optimize against explicit rewards. The planned Echo rewards should use observable task outcomes, valid tool calls and appropriate approval behavior; a fluent self-report is not an outcome check. GRPO was introduced in [DeepSeekMath](https://arxiv.org/abs/2402.03300); [TRL's GRPO documentation](https://huggingface.co/docs/trl/main/en/grpo_trainer) covers reward functions and supported multimodal training.
3. **Evaluate and run locally.** Compare against the starting model on held-out tasks, including tool validity, grounding, task success, failure recovery and unauthorized-action behavior. Measure local latency, memory and vision-runtime compatibility before claiming practical local performance.

The repository contains an [experimental QLoRA/SFT script](../deepakllm/train/train_lora.py) that explicitly says it has not been verified on real training hardware. Synthetic generation, reviewer tooling, GRPO rewards/rollouts and the complete training/evaluation pipeline remain planned work. The target base model, final artifacts and deployment format have not been fixed by this documentation update.

## Refresh the inventory

```bash
npm run dataset
node scripts/dataset-inventory.mjs
```

The second command outputs aggregate JSON only and supports `--trajectories-dir DIR`, `JARVIS_TRAJECTORY_DIR` and `ECHO_DATA_ROOT`. It does not export tasks, screenshots or raw model messages. To deliberately refresh the checked-in aggregate record after review:

```bash
node scripts/dataset-inventory.mjs > docs/dataset-inventory.json
```

Update the dated prose and tables alongside the JSON; do not silently present old totals as live counts. Raw data and model weights remain outside this documentation commit.
